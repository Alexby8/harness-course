# Архитектура BotGate

BotGate состоит из основного приложения на российском сервере и заменяемых
зарубежных proxy-нод. Перенос инфраструктуры завершён; прежний сервер удалён
и в рабочей схеме не участвует.

## Основной сервер

Laravel-приложение из `bot-gate-main/` отвечает за:

- пользователей, ботов и зашифрованные Telegram-токены;
- публичный API, проверку доступа и ограничения запросов;
- бизнес-логику, постоянные данные и очереди доставки webhook;
- Filament-админку, конфигурацию, выбор и мониторинг proxy-нод.

Production: `bot-gate.ru`, каталог `/var/www/bot-gate.ru`.
Dev: `dev.bot-gate.ru`, отдельный каталог `/var/www/dev.bot-gate.ru`.
Постоянные данные хранятся на основном российском сервере.

## Proxy-ноды

`bot-gate-proxy/` — отдельный Go-сервис, запускаемый в Docker на зарубежных VPS.
Нода проверяет подпись внутренних запросов BotGate и передаёт их в Telegram.
Поддерживаются JSON-запросы, multipart-загрузка и потоковое скачивание файлов.

Ноды stateless: бизнес-логика и постоянное хранение пользовательских данных
остаются в Laravel. Данные запроса обрабатываются нодой для передачи в Telegram;
stateless не означает отсутствия такой обработки.

## Взаимодействие и отказоустойчивость

Основной маршрут обращения к Telegram:

```text
Клиент → публичный API Laravel → выбранная Proxy Node → Telegram Bot API
```

Laravel проверяет доступ клиента и выбирает ноду среди `enabled + online`.
Меньшее числовое значение priority имеет преимущество. Клиенту не нужно
выбирать ноду или знать её адрес; публичный контракт сохраняется при её замене.

При наличии резервной ноды возможен failover. Запрос с неопределённым
результатом нельзя автоматически повторять: операция могла уже выполниться
в Telegram, а повтор может создать дубликат.

Проверка `/health` контролирует доступность proxy-сервиса. Периодическая
проверка Telegram не используется. Для проверки конкретной сохранённой ноды
предусмотрена ручная отправка тестового сообщения из Filament.

## Входящие Telegram webhook

```text
Telegram → общий webhook HTTPS-домен → Nginx выбранной зарубежной ноды
         → основной Laravel → webhook_events + jobs → очередь webhooks → клиент
```

Каждая нода получает отдельный Nginx virtual host из
`bot-gate-proxy/deploy/nginx/webhook.conf.template`. Он принимает только POST
входящего webhook-маршрута и обращается к фиксированному основному HTTPS-host
с проверкой сертификата и SNI. Go и его исходящие JSON/multipart/file endpoints
не участвуют в приёме. Успех возвращается только после ответа Laravel;
неопределённые POST нода не повторяет. Очереди и постоянных событий на ноде нет.

Входящая нода выбирается A-записью общего домена. Laravel `priority`, `enabled`
и `online` управляют исходящим транспортом, но не переключают входящие webhook.
Stateless Nginx не заменяет надёжную очередь при недоступном основном сервере:
возвращает ошибку, а Telegram отвечает за повторную доставку.

`TELEGRAM_WEBHOOK_BASE_URL` независимо от `APP_URL` задаёт адрес новых регистраций.
Пустое значение сохраняет исходный маршрут на `APP_URL`. Общий URL-сервис
используют регистрация, resync, кабинет и `botgate:webhooks:sync`.
Старый endpoint остаётся доступен. При частичном переносе доверяются только
точные URL конкретного бота на `APP_URL`, текущем адресе приёма и перечисленных
в `TELEGRAM_WEBHOOK_ALLOWED_BASE_URLS` origins. Prod/dev имеют отдельные значения.

Приём блокирует строку бота в транзакции основной БД, проверяет пару
`bot_id + telegram_update_id` и сохраняет событие, `queued_at`, статистику и
database-job атомарно. Соединение очереди `webhook_ingress` использует ту же
основную БД и таблицу `jobs`; перевод его на Redis/другую БД или `after_commit`
нарушит эту гарантию. Worker должен читать эту таблицу и очередь `webhooks`.
Без `update_id` каждый payload остаётся отдельным событием.

Повтор принятого update не создаёт новую доставку. Для старого `pending` события
с нулём попыток и без `queued_at` повтор восстанавливает задачу; атомарная проверка
номера попытки защищает от двух одновременно исполняемых копий задачи.
Миграция добавляет обычный индекс, не unique, и сохраняет исторические дубликаты.
Дедупликация действует пока событие хранится (существующая очистка — 30/60 дней).
Она не обещает exactly-once на сервере клиента: при потере ответа клиента
сохраняются прежние повторы доставки с тем же `X-BotGate-Event-Id`.

Порядок DNS/TLS, ограничения логирования, перенос и откат описаны в разделе
«Входящие webhook» [runbook](proxy-node-runbook.md#15-входящие-webhook-на-каждой-ноде).
