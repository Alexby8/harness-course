# Домашняя работа после урока 5 · независимая проверка руководства

В редакционном плагине BotGate появился [рецензент](../agents/botgate_reviewer.toml). При каждом запросе новой статьи редактор готовит пакет, затем рецензент в отдельном контексте отвечает на исходный вопрос читателя. Для зачёта он должен показать, где в статье обоснована каждая существенная часть ответа. Если информации недостаточно, он возвращает конкретный пробел редактору. [Команда, управляющая циклом](../skills/guide-package/SKILL.md) · [Критерий приёмки](../skills/review-guide/SKILL.md).

## Что проверяли

> Как настроить список команд так, чтобы в личном чате пользователь видел /order, а в группе — /rules, и что произойдёт, если участник группы сам введёт /order?

Ожидаемый результат — владелец бота выбирает настройки для двух типов чатов и понимает, где ограничивать выполнение команды. Это объясняющая статья. Критерий применяется к смыслу ответа и подходит для материала без исполняемого примера.

Оба раза использовали одну учебную копию BotGate, те же 16 опубликованных статей, один slug и один пользовательский запрос. Первый пакет переместили в архив до второго запуска, чтобы проверка на дубликаты не подменяла повторное написание статьи. Рецензенту передавали вопрос, ожидаемый результат и JSON проверяемой версии. Редактор и рецензент работали на `gpt-6.2-sol` с `high`.

<summary>Одинаковый запрос в обеих сессиях</summary>

```text
$botgate-editorial:guide-package Подготовь одно короткое объясняющее руководство для владельца Telegram-бота. Вопрос читателя: «Как настроить список команд так, чтобы в личном чате пользователь видел /order, а в группе — /rules, и что произойдёт, если участник группы сам введёт /order?» Ожидаемый результат: читатель сможет выбрать настройки меню для двух типов чатов и решить, где обеспечить ограничение команды. Используй slug telegram-command-menu-scopes. Это разбор выбора, без требования писать код. Работа в учебной копии, проверка пакета только через dry-run.
```

</details>

## Два запуска одной задачи

| Что измерили | Исходный плагин 1.1.2 | Плагин с рецензентом 1.2.0 |
| --- | --- | --- |
| Готовый пакет | [Версия до изменения](before/telegram-command-menu-scopes.json) | [Версия после изменения](../../../content/guides/packages/telegram-command-menu-scopes.json) |
| Время команды подготовки | 178 секунд, завершилась после технической проверки | 169 секунд, включает техническую проверку и независимую приёмку |
| Время до решения независимого рецензента | 221 секунда суммарно: 178 на подготовку и 43 на отдельно вызванного рецензента | 169 секунд в одной команде |
| Пробелов в ответе первого черновика | 0 · `PASS` | 0 · `PASS` |
| Исправлений по замечаниям | 0 | 0 |

**До изменения.** В разделе `choose-scopes` рецензент нашёл обе настройки меню. В `manual-command` автор объяснил, что участник может ввести скрытую из подсказок команду вручную. В `enforce-in-handler` указано, где проверять тип чата до оформления заказа. Исходный плагин сам завершил работу после dry-run; для оценки черновика отдельно запустили новую сессию с тем же профилем рецензента и тем же критерием.

**Что уточнили после первого запуска.** Редактор получает исходный вопрос и явно отвечает на каждую его существенную часть. Рецензент восстанавливает ответ из самой статьи и указывает разделы и фрагменты, которыми его обосновывает. Замечание возвращается редактору для правки того же файла. На повторной проверке рецензент получает свежий контекст. Допускаются две попытки исправления, затем команда возвращает оставшиеся замечания пользователю.

**После изменения.** Рецензент указал `choose-scopes` для двух настроек и `manual-command` для ручного ввода и проверки типа чата в обработчике. Обе версии отвечают на вопрос с первого раза. В этом эксперименте число ошибок не снизилось. Изменился наблюдаемый результат команды: вместе со статьёй пользователь получил независимый ответ читателя с основаниями. Одной пары запусков недостаточно для оценки обычной скорости плагина.

Оба JSON отдельно прошли `php artisan guides:import <путь-к-файлу> --dry-run` с одинаковым выводом `Validated: 1; changed: 1.`. SHA-256 учебной SQLite до и после контрольного dry-run совпал; в ней 16 опубликованных статей. Вызовы к реальному боту не входили в задание.

## Контрольная проверка с пропущенным ответом

В отдельной копии первого пакета оставили раздел `choose-scopes` и нейтральное вступление. В ней по-прежнему есть ответ про две настройки меню, но отсутствуют разделы про ручной ввод команды и решение обработчика. Запуск относится только к проверке механизма исправления и не включён в таблицу выше.

Штатный dry-run снова вернул `Validated: 1; changed: 1.`. Независимый рецензент за 43 секунды вернул `REVISE` с одним замечанием:

> Нужно пояснить, может ли команда, введённая вручную, попасть в обработчик бота и где проверять тип чата, если оформление заказа должно быть доступно только в личном чате.

Редактор исправил ту же контрольную копию. В разделе `choose-scopes` появились условия доставки введённой вручную команды и место проверки `message.chat.type` до начала оформления заказа. Повторный dry-run прошёл. Новый рецензент получил исходное задание и исправленный JSON, подтвердил ответ по разделу и вернул **`PASS`**. Контрольная копия не меняла ни один из двух сравниваемых пакетов.

При пересказе решения координатор посчитал два связанных уточнения внутри замечания как два пробела. В первичном вердикте рецензента это одно замечание. Поэтому для версии 1.2.1 зафиксировали формат первой строки и передачу числа замечаний без пересчёта. Критерий приёмки остался тем же. При повторной оценке той же неполной копии рецензент версии 1.2.1 вернул `REVISE · 1` и одно пронумерованное замечание.
